# Agent Note: 等条件：把"等一会儿"换成"等某个状态，并回报到没到"

Status: implemented

## Problem

[09-28 那轮真机](../../proposed/testing/2026-09-28-local-spa-drive-frictions.md) 的第 4 条：等待应用层就绪（引擎冷启动 1 s 到几十秒、连接 + 加载想定 12 s）时没有原语，只能**手写 6 次 `await new Promise(r => setTimeout(r, 8000))`**。固定 sleep 在两个方向上都错：短了就误判"它没反应"（同一轮里因此判定过一次空操作），长了就把对话的时间花在等待上，而且**等待期间没有任何信息**——sleep 的返回值是 `undefined`，模型拿不到任何"现在到哪一步了"。

而 [工具面优化](../feature/2026-09-24-tool-surface-optimization.md) 那一轮明确决定了"**不做独立的 `wait_for` 工具**"，理由是"新能力优先做成参数，不轻易加工具名"（当时的对照数据是 chrome-devtools `--slim` 只有 3 个工具、Anthropic 的"更多工具不等于更好"）。所以这一项不是补一个缺口，而是**推翻一个既有决定**——要么有足够好的理由，要么维持现状。

## Decision

加第七个工具 **`browser_wait`**，形状刻意贴着已有的定位词汇：

- **条件恰好一个**，五种：`text`、`role`(+`name`)、`selector`（这三个就是 `browser_click`/`browser_type` 的定位参数，同一套名字、同一个解析器）、`url`（地址里的大小写不敏感子串）、`time`（固定等待，最后手段）。给了两个**拒绝**并说清理由，理由是"一个会挑其中一条的等待，会在调用方等的是另一件事时把页面报成就绪"。
- **超时是值，不是错误**：条件没成立时返回 `matched: false` + `waitedMs` + 当前 `url`/`title` + 这期间页面改了什么（复用 [变更清单](2026-09-29-action-report-changes.md) 的探针，**在第一次询问之前**装上）。理由是硬性的：PTC 下未捕获的异常会直接判 `CODE_RUN_FAILED`，而"还没就绪"是正常分支；native 下把"它没到"报成错误卡，也会让模型以为是自己写错了。
- **不抛异常，但**这些仍然是错误（可捕获、指名下一步）：没有打开的页面（不要去 `ensure()` 一个空白浏览器再等它）、同一条件/多个条件、`time` 比 `timeoutMs` 还长、`timeoutMs` 超过上限、页面拒绝的 selector（一个打错的 selector 应当立刻失败，而不是被轮询 10 s）。
- **上限三件套**：`timeoutMs` 默认 **10 s**、最大 **30 s**，工具自己的 `timeoutMs` 是 **45 s**。差值是故意的——等待的上限必须**小于**调用自己的预算，否则两者同刻到期，"没等到"会被报成"调用被切断"。
- **轮询间隔 250 ms**：每次询问树形态的条件就是一整棵无障碍树，所以这是折中而不是轮询频率；判断在**读截止时间之前**做一次，最后一刻成立的条件仍算命中。
- **匹配到 ≥1 个就算到**，并把**候选数**带回去（`matches`）：条件"这样的元素在"确实成立了，而多于一个意味着**接下来的点击会被判为歧义而拒绝**——这个数就是让调用方知道该收窄的那一半。
- **命中时回报的是页面给的答案**（`element` 的 role+name，来自无障碍树），不是调用方写的那句条件。
- **它等已经打开的那一页**，不会为了等而启动浏览器：一个从不存在的页面上等 10 s 没有任何意义。

## 参照系实测（2026-09-29；同 [探针](../../../../.prove/zcode-action-surface.mjs) 那一批产物）

- **等待在参照系里是一等原语**，而且**只等页面状态**：`locator.waitFor({state: "attached"|"detached"|"visible"|"hidden", timeoutMs?})`、`page.waitForLoadState({state?, timeoutMs?})`、`page.waitForURL(url, {timeoutMs?, waitUntil?})`、`expectNavigation(action, {url?})`。`networkidle` 明确**不支持**。
- **没有谓词等待**：`waitForFunction` / `poll` 一处都没有。连它也不给"轮询任意表达式"——那件事在我们这里归 `browser_evaluate`（`wait` 因此**不做 `expression` 条件**，见替代方案 3）。
- **预算**：常规定位/URL/加载态等待"默认 3000 ms，且请求更大的值也封顶在 3000 ms"；固定等待是**独立命令** `tab.playwright.waitForTimeout(ms)`，并在文档里被明确劝退（"Prefer a targeted wait or fresh `domSnapshot()` over routine sleeps"、"for the rare case where no concrete page state can be observed yet"——与我们把 `time` 定为最后手段同一条理由）。长活儿的官方答案是**拆成多次调用**：REPL 那一格 "…If that exceeds the 120000 ms maximum, split the work into multiple calls."（**120 s 与我们的 `browser_evaluate` 完全一致**）。
- **`expectNavigation(action)` 是"先装等待器，再动作"**，还提醒"已加载的旧页面可能直接满足它"，要用 `{ url }` 证明真的换了页面。这与我们 `armSettle()`/`wait()` 都**在动作或第一次询问之前**装好观察者是同一条原理。
- **失败纪律**：超时/严格模式/解析失败之后**不许重试同一个定位器**，要重新取快照重建。这条只对"超时能带回信息"的等待才可执行——正是我们让超时返回现状与变更清单的原因。
- **一个明确的分歧**：它的 3 s 封顶意味着**一次调用等不了 30 s**，只能由模型在外层循环里反复重试；我们的 30 s 是因为 native 下一次等待就是一次完整的工具往返（`sleep` 的成本在这里比它那边高得多），而 PTC 下更是整段程序里的一次 `await`。

## Alternatives considered

1. **只写 skill 模板（async IIFE + 轮询），不加工具。** 这是原方案的另一半，也是"不加工具名"规则下最保守的选项。放弃的理由不是"参照系有"，而是 09-28 的实测：模型当时**没有**发明轮询，而是写了 6 次固定 sleep——文档能救"不知道怎么写"，救不了"不知道该等什么"；而且手写轮询**不会回报"没等到 + 页面现在是什么样"**，那恰恰是判断下一步需要的信息。决定加工具之后，skill **不再**写轮询模板（同一件事不留两个家）。
2. **做成既有工具的参数**（例如 `browser_click({..., waitFor})`、"动作前先等条件"）。等待是一个**独立步骤**，不是动作的修饰：09-28 的那 6 次等待里，多数发生在**动作之前**（等引擎起来），而"动作之后"的那一半已经由 settle 覆盖。做成参数还得给每个工具加同一组参数，等于把定位词汇的那套共享复制到四个工具上。
3. **加 `expression` / 谓词条件**（等一个 JS 表达式为真）。表达力最强，但它与 `browser_evaluate` 完全重叠（后者有 120 s 预算、能 await、能自己写循环），并且会把"页面状态"与"任意代码"混进同一套词汇里——参照系也没有这一轴。放弃：要写谓词就走 `browser_evaluate`，要等页面状态就用 `wait`。
4. **超时抛异常**（与定位未命中一致）。一致性好，但代价错了：定位未命中意味着**接下来什么也做不了**，而等待超时意味着**"现在还没到"**——一个正常的中间状态。PTC 下未捕获异常直接判整段程序失败，native 下错误卡会读成"我写错了"。放弃。
5. **让命中的等待直接回一个 ref**，省掉随后的快照。ref 是**快照发出的标签**（见 AGENTS.md 的"ref 属于页面"），凭空 mint 一个模型从没在任何树里见过的 `e<n>`，等于给它一个无法与快照对照的句柄；而且会把 `wait` 变成"偷偷做了一次快照"。放弃：回报 role+name，要 ref 就取快照，要动作就用同一句定位。
6. **照抄参照系的 3 s 封顶**。那在它的架构里合理（REPL 里一次等待是一次廉价方法调用，模型在外层循环），在我们这里是错的：每次等待都是一次完整的工具往返，3 s 封顶会把"等引擎起来"变成十几次调用。放弃，但**上限仍然是必须的**（30 s），否则等待就变成了"调用不会回来"。
7. **命中多个就拒绝（与定位一致）**。语义上"等一个唯一的元素"更整齐，但会让"页面上有两个『就绪』"这类本来可以继续的情况变成又一个失败；条件"存在这样的元素"确实已经成立。放弃，改为**命中即成立 + 回报候选数**，把"点击会被拒"这件事说清楚。
8. **等一个 ref 失效/出现**（`wait({ref})`）。ref 只对"这份文档的这一次回答"有效，等待跨的正是"页面变了"这件事——拿一个即将失效的句柄去等它自己，是本末倒置。放弃：`browser_wait` 不收 `ref`（这也是 `LOCATOR_PARAMETERS` 与 `TARGET_PARAMETERS` 要分开的原因）。

## Consequences

- **工具面从 6 个变成 7 个**，这推翻了 [工具面优化](../feature/2026-09-24-tool-surface-optimization.md) 里"不做独立的 `wait_for` 工具"的决定；理由与代价都记在那一篇的对应行上（部分取代，两篇互相链接）。第七个工具的**新增词汇量被刻意压到一个动词**：条件用的是 `browser_click`/`browser_type` 已有的四个参数名 + `url`/`time`，没有第二套定位语言。
- **`LOCATOR_PARAMETERS` 与 `TARGET_PARAMETERS` 分开**：前者是四个定位参数（`browser_wait` 用），后者再加 `ref`（动作工具用）。同一条"要不要收 ref"的差别在一处常量里表达，不再是两份参数表。
- **PTC 门禁当场要求补行**：`PTC_CALLS` 加了 `browser_wait: { text: "Send", timeoutMs: 200 }`，并断言 `matched === true` 与 `waitedMs` 是数字——即"超时/命中都是程序能分支的值"这条契约真的过了桥。（可见工具面恰好等于那张表的断言在门禁里，漏了就红。）
- **每次询问的成本**：树形态的条件是**一整棵 `Accessibility.getFullAXTree`**，所以一次 10 s 的等待默认约 40 次读取；`url` 与 `time` 条件不读树（有断言钉住）。
- **等待期间的变更清单是"刚开始那一段"**：探针仍在第一次询问之前装上，但它按 settle 语义在页面安静 500 ms（或 3 s 上限）时就结算了，所以清单说的是**等待开始时页面的那一波反应**，不是整个等待窗口里的全部变化——足够回答"我等的东西是不是正在被做出来"，但别把它读成完整日志。
- **取消后循环还会跑一小会儿**：`cancelable()` 会立刻放弃调用并让页面停下，但轮询循环没有自己的信号，会一直跑到等待的截止时间（上限 30 s），最多每 250 ms 发一次读。它是有界的（不是"永不返回"），而放弃后的拒绝由 `cancelable()` 的 `void started.catch()` 兜住，不会变成未处理拒绝。要真正中断它，得给浏览器方法传信号——那是与现有约定不同的一层，本轮没做。
- **继承无障碍树的两条盲区**：`wait` 的条件（除 `selector` 与 `url` 外）读的是无障碍树。**同进程 iframe 的内容现在会拼进这棵树**（[子帧那一篇](../bug-fix/2026-09-29-frame-splice-never-ran.md)），所以这一条收窄成 **跨进程（OOPIF）帧里的元素等不到**；`selector` 走 DOM 可以触达影子根与同源帧，`url` 不受影响。
- **真机回归 [23] 在第一次跑的时候就抓到一个定位层缺陷**（这是本轮最有价值的产出之一）：真机上 `{ text: "engine ready" }` 同时命中了元素**和它内部的文本 run**（按钮这类角色会从内容计算无障碍名），于是 `matches: 2`，而命中的 `element` 是那个 run——run 是**任何动作都够不着**的东西（快照从不给它 mint ref），随后的点击还会因为这个假歧义被拒。修法不是简单丢弃文本 run：`<div>Loading…</div>` 这种普通容器**自己不算名字**，run 是唯一说得出话的节点，丢了它，"等页面上的那句话"就再也等不到了。所以规则与快照的过滤同源——**祖先已经说过同一句话的 run 不算第二个答案**；完整规则落在 [定位参数化](2026-09-29-locator-parameters.md) 里。同一次真机还纠正了一个想当然的假设：`role="status"` 的 `div` **不会**从内容取无障碍名（第一版 fixture 就是照那个假设写的，红过一次）。
- **真机那一条已经量过**（`scripts/snapshot-regression.mjs` 的 [23]，`data:` fixture、离线）：元素 1200 ms 后出现，等待在 **797 ms** 命中（不是耗完 8 s 预算）；问一个还不存在的状态 → `matched: false`、`waitedMs 509`（预算 300 ms）；地址条件不读树即可命中；**用同一句 `text` 定位去点等到的那个元素成功**（"等到的东西能被操作"）；`matches === 1`（run 没有被算成第二个答案）。整轮真机 59/60，唯一的红仍是与本项无关的数据依赖断言（`github.com/trending` 今天 199 节点、阈值 `> 300`）。
- 覆盖：**17 条新用例**（`session-browser.test.ts` 10 条：提前命中、超时、地址、固定等待、没有页面可等、超时也带变更清单、selector 被拒只问一次、命中多个报候选数、不读树的两种条件、元素与文本 run 只算一个；`locate.test.ts` 2 条：run 被祖先覆盖时不算第二个答案、容器没名字时 run 仍然可找；`tools.test.ts` 5 条渲染），另在既有的 `ptc.test.ts` 用例里加了门禁行与"`matched` 是值"的断言。全套从 336 涨到 **353**（真 `pnpm test` 与无隔离各跑一次，均 exit 0）。
